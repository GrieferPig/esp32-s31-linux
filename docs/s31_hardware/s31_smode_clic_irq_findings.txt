ESP32-S31 SMP CLIC lockout findings
Updated: 2026-08-21

Question and final conclusion
-----------------------------
CoreMark followed by SIGINT could leave the shell permanently unresponsive on
two Linux harts. The final diagnosis has two distinct parts:

1. An old Linux image incorrectly enabled SBI RFENCE. TLB shootdowns entered
   OpenSBI, sent M-mode software IPI ID3, and could deadlock while both harts
   were in IRQ-disabled kernel critical sections.
2. After switching to native S-mode IPIs, S31 could still retain an S CLIC
   return/active state in which a slot remained IP=1, IE=1 and SIE=1 but the
   hart did not enter its handler. This affected timer/IPI and ordinary device
   interrupts, so replacing only the IPI transport was insufficient.

The current solution keeps runtime SMP IPIs and RFENCE entirely in S-mode,
uses a non-nested native SYSTIMER/doorbell layout, and adds an idle software
recovery path that dispatches every enabled pending S external slot through its
normal Linux handler.

Evidence for the original SBI RFENCE deadlock
----------------------------------------------
- `riscv_sbi_for_rfence` was 1 in the old image although the S31 irqchip was
  intended to provide native IPIs.
- The failing path was Linux remote sfence -> OpenSBI sbi_tlb_request() ->
  M-mode IPI ID3. Both harts could have SIE=0 inside spin_lock_irqsave while
  OpenSBI waited for completion.
- The CLIC driver now calls riscv_ipi_set_virq_range() before sbi_ipi_init().
  The architecture sees an existing IPI range, returns without enabling the
  SBI transport, and leaves `riscv_sbi_for_rfence=0`.
- Runtime reschedule, call-function and TLB-shootdown IPIs use HP_SYSTEM
  doorbells ID40/41 and no longer enter OpenSBI.

Evidence for the native S-mode acceptance lockout
-------------------------------------------------
- Preserved failures showed the target in or near idle with:
      sstatus.SIE = 1
      native slot IP = 1
      native slot IE = 1
      doorbell = 1 in IPI cases
  The notification was present in hardware, but no S handler was accepted.
- The OpenSBI machine-trap recorder reported no runtime ID21 in these failures.
  Radio was disabled with `esp32s31_radio=off`. ID21 must therefore not be
  blamed without an actual recorder hit.
- Commit 63410ef was not contrary evidence: it used a single Linux hart and did
  not exercise SMP reschedule, call-function or remote TLB shootdown paths.

Cross-privilege 0xff state
--------------------------
- A controlled bootloader probe proved that an M-mode CLIC interrupt crossing
  from S-mode creates a supervisor 0xff sentinel independent of the M interrupt
  level. Copying complete raw M cause metadata to S-mode can propagate that
  state into a later S return boundary.
- Logical dispatch must always mask xcause with 0xfff. Full raw xcause restore
  is valid only for returning from the corresponding real CLIC interrupt.
  Synchronous M/S redirects must carry only the low logical cause.
- Restoring arbitrary SPIL values or trying to repair sintstatus from Linux was
  unsafe. A conditional SPIL sanitizer corrupted a userspace return in an
  earlier experiment. The current design instead forbids S interrupt nesting
  and owns a separate raw return token.

Rejected or incomplete approaches
---------------------------------
- IPI level 7: one SIGINT sequence improved, but a later sequence stalled.
  A higher-level IPI can also meet a cross-privilege return boundary and adds
  nesting state that S31 does not restore reliably.
- Separate SYSTIMER ID42/43 and IPI ID40/41: still stalled.
- Combining SYSTIMER and IPI into one level-1 slot: reduced the frequency but
  did not eliminate lockout by itself.
- MNLBITS changes, `nohlt`, threshold rewriting, doorbell readback/reassert and
  request/ack recovery: useful diagnostics, not complete fixes.
- M-mode PLIC-style aggregation followed by one S ID1 notification: still left
  ID1 pending and unaccepted, while increasing cross-privilege interrupts.
- Synthetic exception/sret recovery: unsafe; a probe became stuck in exception
  table lookup and an extra sret pops CLIC return state twice.
- Completely removing OpenSBI: not currently valid. Direct S-mode access to
  local MTIME/MTIMECMP faults, and boot/HSM/reset still require M-mode services.
  The performance-sensitive SMP IPI/RFENCE path has nevertheless been removed
  from OpenSBI.

Final native layout
-------------------
- All S-mode timer, IPI and device slots use level 1; nesting is disabled.
- Doorbells:
      hart0 -> hart1: 0x20586014/source66/raw ID40
      hart1 -> hart0: 0x20586010/source65/raw ID41
- SYSTIMER TARGET0/source33 shares hart0 ID41; TARGET1/source34 shares hart1
  ID40. The handler drains both asserted sources from the shared slot.
- Linux uses SYSTIMER counter1 and per-hart one-shot targets rather than direct
  S-mode CLINT compare access.

Software pending recovery and the ID31 proof
--------------------------------------------
- Forced IRQ-enabled idle polling checks doorbell, SYSTIMER status and every
  enabled external CLIC ID16..47 with local interrupts disabled.
- A pending doorbell is cleared before ipi_mux_process(). A pending timer calls
  the ordinary RISC-V clockevent handler. Other IDs are passed to
  generic_handle_domain_irq(), preserving each device driver's acknowledgement
  and wakeup rules.
- The first poller version handled only timer/IPI. It completed 20 SIGINT task
  exits, then serial output stopped between `SIGTEST20:rc=130` and its newline.
  JTAG found both doorbells clear and both harts idle, but hart0 ID31 was
  IP=1, IE=1. ID31 is AHB-GDMA TX4/source45, used by UHCI/UART0 DMA pair4.
  General external-slot polling dispatched its normal completion handler and
  removed the half-line serial stall.
- Software timer dispatch initially panicked with "Fatal exception in
  interrupt". The saved frame showed a load page fault at tick_periodic() from
  bad address 0x80000000: get_irq_regs() was invalid because no hardware trap
  frame existed. The poller now installs a zeroed kernel-mode pt_regs with
  set_irq_regs(), surrounds dispatch with irq_enter/irq_exit, and restores the
  prior pointer afterward.

Validation and remaining boundary
---------------------------------
- Final flashed xipImage SHA-256:
      8e0ef27a49b0abdb8e4744c16b2422f541cac2e58b6d690abc069c44bb844b74
- With CPU1 hotplugged, the recovery image passed:
      30/30 exact CoreMark SIGINT tests, then 10/10 on the optimized image
      dual CoreMark TERM with status 143/143
      200 affinity round trips
      two complete pinned dual-CoreMark runs
      final scores 1048.22 + 1063.60 iterations/s
- A longer run recorded timer IRQs 26255/23743, ID31 count 922, reschedule IPI
  562/518 and call-function IPI 2325/2739, then returned `FINAL_ALIVE` with
  CPUs 0-1 online.
- This validates radio-off SMP, hotplug, signal teardown, native IPIs, device
  completion recovery and sustained dual compute. Wi-Fi/BT remains outside
  this validation. If a future stall records ID21, capture the OpenSBI trap
  recorder before attributing it to the blob.
- Recovery currently runs at idle polling points. A future workload that
  proves both harts can remain permanently non-idle while CLIC acceptance is
  locked would require an additional safe polling point; that condition was
  not observed in the completed dual-CoreMark tests.

方案基本可行，而且这正是正确的演进方向。下面是逐项分析：
FPU 确认
blob 全部 72 条 FPU 指令里，s31_rtos_switch 的保存/恢复就占了 26 条（12×fsw + 12×flw + frcsr + fscsr）。剩下的约 46 条大概率在 printf 浮点格式化、mbedtls 冷门路径里。闭源 WiFi MAC ISR 本身只做寄存器读写 + memcpy + 位操作，不需要 FPU。改用 kthread 后上下文切换由 Linux 完成，那 26 条直接消失。如果真遇到 FPU 指令执行，会立即 trap 成 kernel oops，可以到时候在 threaded IRQ handler 里包一个 kernel_fpu_begin/end 兜底。
可行性映射
当前 gate 模型	提议的 kthread 模型
单一 worker kthread + gate	每个 FreeRTOS 任务 = 一个 Linux kthread
s31_rtos_switch 手写上下文切换	删除，用 Linux 调度器
hardirq → wake → gate → 跑 ISR	request_threaded_irq，线程化 IRQ 直接跑 blob ISR
gate 内 kernel_fpu_begin	不需要
TIMG1 tick → wake_up → gate	直接 jiffies/schedule_timeout
队列 block → 手写切栈	wait_event_interruptible_timeout
FromISR → 标记 pending 等 gate	wake_up() 直接唤醒 kthread
gate 内整段关中断	只有 vPortEnterCritical 等价 local_irq_save（单核够用）
收益
当前 idle 时最痛的 10ms tick 下界直接消失：
- 帧到达 → IRQ 线程立即跑 blob ISR → 唤醒 WiFi kthread → 立即处理 → netif_rx
- 预计 ISR→帧投递延迟从 avg 350us / peak 6ms 降到稳定 <100us
- 吞吐瓶颈（现在 ~8KB/s）应该会显著改善
需要重写的部分
1. s31_rtos_core.c：删掉 s31_rtos_switch / schedule / 就绪队列；xTaskCreatePinnedToCore → kthread_create + wake_up_process，vTaskDelay → schedule_timeout，vTaskDelete → kthread 退出
2. s31_rtos_queue.c：block/wake 改成 wait_event_* / wake_up，队列数据结构可保留
3. esp32s31-radio-smode.c：
- s31_radio_hardirq → 最小化或直接用 request_threaded_irq，线程 handler 里直接跑 registration->handler(registration->arg)
- esp_intr_enable/disable → 直接 enable_irq/disable_irq_nosync（不再需要 deferred sync）
- 删掉 gate 的 kernel_fpu_begin / 私有异常栈切换 / init_mm 切换逻辑中的大部分
4. 每个 blob kthread 启动时 kthread_use_mm(&init_mm)（ROM 0x2f800000 恒等映射需要）
风险点
1. FPU：上面分析过，大概率没有，但要在板上验证；留一个 kernel_fpu_begin/end 兜底位置（threaded IRQ handler 里）
2. 异常栈：当前用私有异常栈是因为担心 PHY cache 切换时 PSRAM 栈不可用导致无法保存 trap frame。WiFi-only 路径（S31_WIFI_ONLY）没碰过这个 case，但建议 blob kthread 栈仍分配在内部 SRAM（用 gen_pool 或静态分配）而不是默认的 PSRAM vmalloc
3. FreeRTOS 语义差异：超时精度（tick=10ms vs jiffies）、优先级映射（IDF prio 23 → SCHED_FIFO 或高优先级 nice）需要一一对应；WiFi driver task 的 prio=23 建议直接映射成 SCHED_FIFO
4. 临界区：vPortEnterCritical/ExitCritical 目前直接操作 sstatus.SIE，kthread 模型下改成 local_irq_save/restore 就行，单核安全
结论
可行，值得做。改动集中在三个文件，blob 链接层（Makefile、wrap flags、ROM linker scripts）完全不动，对外 cfg80211 接口也不动。先确认 FPU 在板上不炸，然后性能应该能上一个量级。
